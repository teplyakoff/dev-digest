# Spec: Project Context — сховище документів, API та складання промпту
Spec ID: SPEC-06
Status: draft
Supersedes: —

Половина фічі, що належить серверу: сховище документів проєкту, три шляхи їх
наповнення, редагування, прикріплення до агентів і скілів, підрахунок токенів, і
заповнення вже наявного слота `specs` у складеному промпті.

Клієнтська половина — [`client/docs/specs/06-project-context.md`](../../../client/docs/specs/06-project-context.md).
Обидва файли мають один `Spec ID: SPEC-06`. Критерії не дублюються: тут
AC-1…AC-16, AC-29, AC-31…AC-40, AC-47, AC-48, AC-51 і NFR-1, NFR-2, NFR-4, NFR-5,
NFR-7, NFR-8; AC-17…AC-28, AC-41…AC-46, AC-49, AC-50, AC-52 і NFR-3, NFR-6 — у
клієнтському файлі. AC-30 відкликано (див. нижче). Повний перелік критеріїв — це
об'єднання двох файлів.

**Наскрізний принцип — найлегша імплементація.** Кожен вибір «менше механіки»
названий явно.

## Проблема й користувач

Користувач має PRD, технічні специфікації та критерії приймання. Рев'ювер їх не
бачить: модель судить про зміну лише за дифом, описом PR і скілами, тож вона не
може сказати «цей код суперечить узгодженій поведінці» — узгодженої поведінки їй
ніхто не показав.

Слот для цього в рушії **вже існує і ніколи не заповнювався**:
`reviewer-core/src/prompt.ts:89-90` оголошує `specs?: string[]` з коментарем
*"Project-context spec chunks (untrusted content)"*, `:213-216` загортає кожен
елемент у `wrapUntrusted('spec-N', …)`, `:293-300` рендерить секцію
`## Project context` і додає її до `PromptAssembly`. Пошук по `server/src` не
знаходить жодного присвоєння `parts.specs`.

Отже, робота — **не проєктувати механізм подачі, а під'єднати наявний**, і
збудувати над ним сховище, яке користувач може редагувати.

## Найважливіше рішення: сховище в базі, а не в клоні

Це найлегше зрозуміти неправильно, тому воно стоїть тут, а не в примітці.

Документи **редаговані**. Редагований документ **не може жити в клоні**:
`server/src/adapters/git/simple-git.ts:77-88` синхронізує клон через
`git fetch` + `git reset --hard origin/<branch>`, з коментарем *"safe here because
we never commit to or run code from the clone"*, а
`server/src/modules/repos/service.ts:110-119` `refresh()` просто ставить у чергу
нове клонування. Будь-який запис у `server/clones/**` знищується наступним
resync або refresh, і до GitHub він не доїжджає ніколи — немає ані гілки, ані PR,
ані креденшелів на запис.

Тому сховище — **у базі**, прив'язане до репозиторію. Рядок `.devdigest/specs/`,
який дизайн показує під заголовком лівої колонки, лишається **написом**, а не
справжнім шляхом у файловій системі: жодного файлу за цією адресою не існує й не
створюється.

Клон усе одно потрібен — але як **джерело імпорту**, не як джерело промпту.

## Goals / Non-goals

**Goals**

- Тримати сховище `.md`-документів на репозиторій, з трьома шляхами наповнення:
  імпорт із клону, новий порожній файл, завантаження файлу.
- Дати редагувати й зберігати текст документа.
- Дати прикріпити документ до агента або до скіла в межах цього репозиторію.
- Підставити текст прикріплених документів у слот `specs` під час запуску агента.
- Записати у трасу, які саме документи потрапили в промпт.
- Показати для кожного скіла, скільки агентів його використовують.

**Non-goals** — кожен названий явно:

- **Жодного запису в клон, у git або в GitHub.** Ані коміту, ані push, ані
  гілки, ані PR. Редагування змінює лише рядок у базі. Закріплено як NFR-8.
- **Жодного чанкінгу й ембедингів.** `code_chunks`
  (`server/src/db/schema/context.ts:31-47`) з `source: ['code','docs','spec']` і
  `embedding: vector(1536)` лишається порожньою та незачепленою.
- **Жодного виклику моделі.** Фіча детермінована.
- **Жодного версіонування документів.** Немає знімків v(n+1), немає історії.
  Наслідок названо в *Open questions*.
- **Жодних тек.** Сховище пласке; кнопку `New folder` з дизайну свідомо не
  реалізовано.
- **Жодного впорядкування прикріплень користувачем.** Порядок алфавітний.
- **Не глоби й не директорії.** Прикріплюється рівно один документ.
- **Не редактор агента і не редактор скіла.** Прикріплення живе виключно на
  сторінці Project Context.
- **Жодної зміни у `reviewer-core`.** Рушій не змінюється взагалі.

## User stories

1. Як рев'ювер, я імпортую `docs/api.md` зі свого репозиторію у сховище, щоб
   показати його агентові.
2. Як рев'ювер, я правлю текст документа прямо на сторінці й зберігаю, не
   торкаючись репозиторію.
3. Як рев'ювер, я прикріплюю документ до конкретного агента і бачу, на скільки
   токенів виріс його контекст.
4. Як рев'ювер, я відкриваю трасу запуску і читаю рівно той текст, що пішов у запит.
5. Як власник воркспейсу, я бачу, скільки агентів використовує скіл, перш ніж його змінити.

## Acceptance criteria (EARS)

Нумерація наскрізна. Ідентифікатори стабільні: там, де предмет критерію вцілів
після зміни, змінено текст і збережено номер; для поведінки, виділеної зі
складеного критерію, додано нові номери; критерій, предмет якого зник, позначено
як відкликаний, а не перенумеровано.

### Кандидати на імпорт із клону

**AC-1.** Система повинна перелічувати всі файли з розширенням `.md` у клоні
репозиторію як кандидатів на імпорт, виключаючи `.git/`, `node_modules/` та
вендорені директорії.

**AC-2.** ЯКЩО кількість кандидатів перевищує `MAX_LISTED_DOCS`, ТОДІ система
повинна повернути перші `MAX_LISTED_DOCS` за алфавітом шляху.

**AC-29.** ЯКЩО список кандидатів було усічено за `MAX_LISTED_DOCS`, ТОДІ система
повинна позначити відповідь як усічену.

**AC-4.** ЯКЩО файл-кандидат на імпорт більший за `MAX_DOC_BYTES`, ТОДІ система
повинна позначити його як `skipped` із причиною «завеликий».

**AC-47.** ЯКЩО файл-кандидат на імпорт не декодується як UTF-8, ТОДІ система
повинна позначити його як `skipped` із причиною «не текст».

**AC-48.** ЯКЩО шлях файла-кандидата виходить за межі клону, ТОДІ система повинна
позначити його як `skipped` із причиною «шлях поза межами репозиторію».

AC-4, AC-47 і AC-48 виділені з одного складеного критерію попередньої редакції.
Кожна причина відмови має власний вердикт, бо кожна має власний шлях коду і
власний спосіб зламатися. Усі три сформульовані проти **імпорту**: після
революції моделі сховища `skipped` є результатом читання кандидата, а не станом
документа, що вже лежить у сховищі.

**AC-5.** ЯКЩО репозиторій не має клону, ТОДІ система повинна відповісти на запит
списку кандидатів `409 { code: 'not_cloned' }`, а не помилкою 500.

**AC-39.** КОЛИ клієнт запитує повторний обхід репозиторію, система повинна
перебудувати список кандидатів із поточного стану клону.

### Сховище документів

**AC-32.** КОЛИ користувач імпортує файл-кандидат, система повинна створити у
сховищі репозиторію документ із текстом цього файлу на момент імпорту.

**AC-33.** КОЛИ користувач створює новий документ, система повинна додати у
сховище документ із заданим ім'ям і порожнім тілом.

**AC-34.** КОЛИ система отримує ім'я та текст `.md`-документа, завантаженого
користувачем із його машини, вона повинна створити у сховищі документ із цим
текстом.

Критерій навмисно нічого не каже про транспорт. Чи браузер прочитає файл сам і
надішле текст звичайним JSON-запитом, чи сервер прийме multipart — це вибір
плану, і обидві форми задовольняють AC-34 однаково.

**AC-35.** КОЛИ користувач зберігає відредагований документ, система повинна
замінити його тіло у сховищі.

**AC-36.** ЯКЩО тіло документа перевищує `MAX_DOC_BYTES`, ТОДІ система повинна
відхилити запис із поясненням і не змінити збережене тіло.

**AC-37.** ЯКЩО сумарний розмір сховища репозиторію перевищив би
`MAX_STORE_BYTES`, ТОДІ система повинна відхилити створення документа з
поясненням.

**AC-38.** ПОКИ репозиторій не має клону, система повинна лишати сховище й усі
операції над ним доступними.

**AC-40.** ЯКЩО два записи в один документ надходять послідовно, ТОДІ система
повинна зберегти останній із них, не відхиляючи його.

**AC-3.** Система повинна повертати для кожного документа сховища кількість
токенів його тіла, що дорівнює результатові токенізації цього тіла, а не оцінці,
похідній від його довжини в символах.

Спосіб перевірити AC-3, не називаючи реалізації: узяти тіло, для якого
токенізація і поділ довжини на чотири дають різні числа, і переконатися, що
повернуто перше з них.

**AC-51.** Система повинна повертати для кожного документа сховища кількість
агентів, які отримають цей документ, що дорівнює розмірові об'єднання двох
множин — агентів, до яких документ прикріплений напряму, і агентів, у яких
увімкнено скіл із прикріпленим цим документом, — де агент, що дістає документ
обома шляхами, врахований один раз.

> **AC-51 рахує «хто це прочитає», а не «скільки прикріплень».** Це не дублікат
> AC-16: той рахує агентів на **скіл**, цей — агентів на **документ**, і
> визначення тут навмисно ширше за пряме прикріплення. Причина в узгодженості з
> рештою фічі: множина, яку описує критерій, — це рівно та, що вже будується для
> складання промпту (AC-9 і AC-10 разом, із дедуплікацією за AC-31), тож число на
> екрані й рядок журналу `Project context: N/M document(s) loaded` (AC-13)
> говорять про одне й те саме. Лічильник, що враховував би лише прямі
> прикріплення, показував би `0` для документа, який насправді потрапляє в промпт
> двох агентів через скіл, — і суперечив би журналу того самого запуску.

### Прикріплення

**AC-6.** КОЛИ клієнт надсилає повний набір ідентифікаторів документів для пари
(агент, репозиторій), система повинна замінити попередній набір цієї пари цим.

**AC-7.** КОЛИ клієнт надсилає повний набір ідентифікаторів документів для пари
(скіл, репозиторій), система повинна замінити попередній набір цієї пари цим.

**AC-8.** Система повинна відхиляти прикріплення документа до агента або скіла
іншого воркспейсу відповіддю `404`.

**~~AC-30~~ — ВІДКЛИКАНО.** Був: «відхилити прикріплення документа, позначеного
`skipped`». Предмет зник разом зі зміною моделі сховища: `skipped` тепер є
результатом **імпорту** (AC-4, AC-47, AC-48), а не станом документа. Файл або
входить у сховище, або ні; прикріпити можна лише те, що у сховищі є, що вже
покривають AC-6 і AC-7. Номер не перевикористовується.

### Складання промпту

**AC-9.** КОЛИ починається запуск агента над PR, система повинна взяти зі
сховища тіло кожного документа, прикріпленого до цього агента для цього
репозиторію, і передати ці тексти у слот `specs` складеного промпту.

**AC-10.** КОЛИ починається запуск агента, система повинна додати у той самий
слот `specs` документи, прикріплені до кожного увімкненого скіла цього агента для
цього репозиторію.

**AC-11.** Система повинна впорядковувати документи у слоті `specs` за іменем за
абеткою.

**AC-31.** Система повинна усувати дублікати у слоті `specs`, щоб документ,
прикріплений і до агента, і до його скіла, потрапляв у промпт один раз.

**AC-12.** ЯКЩО прикріплений документ було видалено зі сховища, ТОДІ система
повинна пропустити його і завершити запуск нормально.

**AC-13.** Система повинна записувати у журнал кожного запуску рядок
`Project context: N/M document(s) loaded` незалежно від того, чи були пропуски.

> **AC-13 і NFR-5 описують одну поведінку, а не дві.** AC-13 — це форма
> критерію: рядок існує і несе обидва числа. NFR-5 — його **порогова форма**:
> частка запусків, у яких рядок присутній, дорівнює 100 %. Реалізується один раз,
> одним рядком коду, і перевіряється одним тестом. Верифікатор не повинен читати
> їх як два незалежні зобов'язання й не повинен зараховувати одне як покрите,
> поки друге не виконано.

**AC-14.** Система повинна записувати у `RunTrace.specs_read` імена саме тих
документів, тіла яких потрапили у промпт.

**AC-15.** ЯКЩО для агента й репозиторію немає жодного доступного прикріплення,
ТОДІ система повинна складати промпт байт-у-байт ідентично до поточного.

### Використання скілів

**AC-16.** Система повинна повертати для кожного скіла кількість агентів, які
його використовують.

AC-17…AC-28, AC-41…AC-46, AC-49, AC-50 і AC-52 належать клієнтові — див.
companion-файл.

## Edge cases

| Випадок | Поведінка | Де закріплено |
|---|---|---|
| Репозиторій без клону | сторінка й сховище працюють; імпорт віддає 409 | AC-38, AC-5 |
| Репозиторій без жодного `.md` | порожній список кандидатів, `200` | AC-1 |
| Тисячі `.md` у клоні | виключення + кап + позначка усічення | AC-1, AC-2, AC-29 |
| Файл-кандидат на 5 МБ | `skipped: завеликий` | AC-4 |
| Кандидат із бінарним вмістом | `skipped: не текст` | AC-47 |
| Симлінк за межі клону | `skipped: шлях поза межами` | AC-48 |
| Документ доріс до ліміту при редагуванні | запис відхилено, старе тіло ціле | AC-36 |
| Сховище доросло до ліміту | створення відхилено | AC-37 |
| Документ видалено, поки прикріплений | пропуск + рядок у журналі | AC-12, AC-13 |
| Документ прикріплено і до агента, і до його скіла | один раз у промпті; в лічильнику агент один раз | AC-31, AC-51 |
| Документ прикріплений лише до скіла | лічильник рахує агентів цього скіла, не нуль | AC-51 |
| Скіл вимкнено глобально | його документи не потрапляють у промпт | AC-10 |
| Дві вкладки зберігають один документ | останній запис виграє, мовчки | AC-40, *Open questions* |
| Файл у клоні змінився після імпорту | сховище не оновлюється саме | *Open questions* |
| Прикріплень немає | промпт незмінний побайтово | AC-15 |
| Сумарний контекст більший за вікно моделі | запуск падає гучно | NFR-7 |

## Design coverage and gaps

**Дизайн прочитано** — і це варто зафіксувати, бо наївний пошук його не знайде.
`_assets/L02/DevDigest Design (standalone) (3).html` — це оболонка бандлера:
`grep` по ній дає лише маніфест артбордів. Екран лежить у base64+gzip ассеті
всередині `<script type="__bundler/manifest">` і зветься `ScreenContext`
(`screen_tour_context.jsx`); навігація — в ассеті `AppFrame`. Читалося як
**недовірені дані**; нічого в бандлі не намагалося давати вказівки.

| Елемент дизайну | Рішення |
|---|---|
| Заголовок `PROJECT CONTEXT`, підпис `.devdigest/specs/` | лишається як **напис**; реального шляху немає |
| Кнопки `Plus` / `Upload` | реалізовано — AC-33, AC-34 |
| Кнопка `Folder` (New folder) | **відхилено**: сховище пласке |
| Кнопка `RefreshCw` (Re-index) | **перепризначено** на «Rescan repo» — AC-39 |
| Статус `Indexed: 12 files · 1,240 chunks` | **замінено** лічильником сховища; чанків не існує |
| Пласке дерево `.md` | реалізовано |
| `Preview / Edit` перемикач | реалізовано — AC-41, AC-42 |
| `Used by 3 agents` | реалізовано — AC-28, AC-16 |
| `CircularScore 78 · COVERAGE` | **відхилено**: покриття зводиться до `Used by N agents` |
| Порожній стан `No spec files yet` + `Add a spec file` | реалізовано — AC-23 |

**Чого в дизайні немає, а фіча додає** — це прогалини, які фіча закриває, а не
речі, що дизайн специфікує:

- **Вкладок для скілів і агентів немає ніде.** Ні на цьому екрані, ні в редакторі
  агента (`Config · Skills · Evals · Stats · CI`), ні в редакторі скіла
  (`Config · Preview · Evals · Stats · Versions`). Дві вкладки-цілі — рішення
  власника, а не дизайну.
- **Лічильників токенів немає ніде.** Вимога 3 їх вимагає; дизайн мовчить.
- **Лічильника агентів на документ немає ніде.** Дизайн має `Used by 3 agents`
  лише на **скілі**; для рядка документа такого елемента він не містить. AC-51 і
  AC-52 вводять його без дизайнерського прецеденту, за формою скілового.
- **Блока проєктного контексту в трасі немає.** `PROMPT_BLOCKS` у дизайні — це
  лише `system`, `repoSkeleton`, `callers`, `user`. Секція Configuration уже
  малює список `Specs read` мононімен, що збігається з наявним
  `RunTrace.specs_read`, але позначеного розгортного блока Prompt Assembly, якого
  вимагає вимога 5, дизайн не містить.

**Стартерові рядки.** `client/messages/en/context.json` частково оживає:
`mode.preview/edit` та `editor.save` **під'єднуються**. Рядок `:13` лишається
неправдою і переписується (AC-27): шляху `.devdigest/specs/` не існує, а
прикріплення явне, тож «кожен агент читає їх» не описує жодної реалізованої
поведінки.

## UX proposals

Поза скоупом, доки не прийнято окремо.

- **UX-1** — показувати, скільки токенів лишилося до вікна вибраної моделі, а не
  лише суму прикріплень. Ціна: ліміт вікна моделі треба донести до клієнта.
- **UX-2** — позначати документ, імпортований із клону, чий файл-джерело відтоді
  змінився. Проблема: сховище тихо розходиться з репозиторієм. Ціна: зберігати
  хеш джерела й порівнювати під час rescan.
- **UX-3** — «оновити з репозиторію» для імпортованого документа. Проблема:
  розходження зараз виправляється лише повторним імпортом вручну. Ціна: конфлікт
  із локальними правками, який доведеться показувати.

## Non-functional requirements

**NFR-1 — security.** Тіло будь-якого документа сховища повинно потрапляти в
промпт **виключно** через слот `specs`, тобто загорнутим у
`wrapUntrusted('spec-N', …)` (`reviewer-core/src/prompt.ts:213-216`), і **ніколи**
всередину довіреної, незагорнутої секції `## Skills / rules`. Поріг: нуль шляхів
коду, що передають тіло документа у `PromptParts.skills`.

Інваріант, не вподобання, і після зміни моделі сховища він **сильніший**: текст у
сховищі має два походження, і обидва небезпечні. Імпортований прийшов із
`server/clones/` — за кореневим `INSIGHTS.md:320-342` це «єдине дерево тут, вміст
якого контролює стороння особа». Створений або завантажений написав користувач, і
він теж не є конфігурацією, якій рушій довіряє. Прикріплення до скіла означає
лише **чи** документ увійде, ніколи — з яким рівнем довіри. Відповідає ASI01
*Goal Hijacking* (`.claude/skills/security/SKILL.md:203`); механізм — не
сканування тексту, а один спільний `INJECTION_GUARD`.

**NFR-2 — storage bounds. Замінює попередню редакцію цієї вимоги**, яка
забороняла зберігати тіла документів у базі. Модель сховища змінилася на
редаговану, тож тіла зберігаються, і замість заборони діють межі: розмір одного
документа не перевищує `MAX_DOC_BYTES = 64_000`, сумарний розмір сховища одного
репозиторію не перевищує `MAX_STORE_BYTES = 2_000_000`. Поріг: обидва
перевіряються перед записом, обидва відмовляють із поясненням.

**NFR-4 — cost.** Фіча не повинна додавати жодного виклику моделі. Поріг: 0 нових
LLM-викликів на будь-якому шляху.

**NFR-5 — observability. Це порогова форма AC-13, а не окреме зобов'язання.**
Частка запусків, у яких присутній рядок `Project context: N/M document(s) loaded`,
повинна дорівнювати 100 % — включно із запусками, де пропусків не було. Правило —
`server/INSIGHTS.md:103-110`: гейт, що звітує лише коли спрацював, не
відрізняється від гейта, який не запускався. Реалізується разом з AC-13 і
перевіряється тим самим тестом; окремого кроку плану не потребує.

**NFR-7 — reliability.** Система не повинна тихо обрізати тіло документа. Поріг:
нуль шляхів обрізання; при перевищенні `WARN_CONTEXT_TOKENS = 20_000` клієнт
попереджає (AC-18), а запуск, що не влазить у вікно моделі, падає гучно.
Обґрунтування — `server/INSIGHTS.md:500-513`: реальний запуск було відхилено на
~937 k токенів, помилка прилетіла на **всі** агенти одразу, без часткового
результату.

**NFR-8 — integrity.** Жодна операція фічі не повинна писати у клон, у git або в
GitHub. Поріг: нуль шляхів запису під `server/clones/**`, нуль викликів git
mutation API з модуля. Прямий наслідок того, що `simple-git.ts:77-88`
синхронізує через `reset --hard`: запис у клон не просто марний, він створює
стан, який зникне без попередження.

## Inputs and provenance

| Вхід | Тег | Примітка |
|---|---|---|
| Список `.md`-кандидатів у клоні | `[deterministic: SourceReader]` | потребує **нового** методу лістингу |
| Текст файлу-кандидата | `[deterministic: SourceReader]` | `read(clonePath, relPath)` уже існує |
| Тіла документів сховища | `[deterministic: postgres]` | нова таблиця, нова міграція |
| Текст завантаженого файлу | `[deterministic: user upload]` | новий зовнішній вхід |
| Кількість токенів | `[deterministic: tokenizer]` | `js-tiktoken` / `cl100k_base` |
| Прикріплення | `[deterministic: postgres]` | нові таблиці зв'язку |
| Кількість агентів на скіл | `[reused: agent_skills]` | join, без нової таблиці |
| Кількість агентів на документ | `[deterministic: postgres]` | join по тих самих таблицях прикріплення плюс `agent_skills`; та сама множина, що й для слота `specs` |
| Слот `specs` у промпті | `[reused: reviewer-core]` | слот уже існує, рушій не змінюється |

**Нових викликів моделі: 0.**

Єдиний справді новий механізм читання — **лістинг директорії**. `SourceReader`
(`server/docs/specs/04-conventions.md:276-288`) має рівно один метод,
`read(clonePath, relPath) → string | null`, і та спека прямо зафіксувала рішення
*"`SourceReader` stays a one-method port instead of growing a directory walk"*
(`:236-238`). Тут воно переглядається: порт отримує другий метод.

## Untrusted inputs

| Вхід | Хто контролює | Правило |
|---|---|---|
| Тіло імпортованого документа | автор репозиторію, тобто будь-хто | `wrapUntrusted` + спільний `INJECTION_GUARD`; NFR-1 |
| Тіло створеного чи відредагованого документа | користувач | те саме — користувач не є довіреною конфігурацією рушія |
| Текст завантаженого файлу | користувач | обмеження розміру (AC-36, AC-37); вміст ніколи не виконується |
| Шлях кандидата з тіла запиту | клієнт | нормалізація через `SourceReader`, відмова на `..` й абсолютні шляхи (AC-48) |

Документ, що містить «ignore previous instructions», лишається даними, бо він
усередині `<untrusted>…</untrusted>`, а системне повідомлення закінчується
гардом. Нічого специфічного для цієї фічі не додається — і це власне й є причина,
чому NFR-1 забороняє обхідний шлях через секцію скілів.

## Open questions

- `[NEEDS CLARIFICATION]` пороги `MAX_DOC_BYTES = 64_000`,
  `MAX_STORE_BYTES = 2_000_000`, `MAX_LISTED_DOCS = 500`,
  `WARN_CONTEXT_TOKENS = 20_000` — числа обрані мною, не виміряні. Найближчі
  орієнтири — `DEFAULT_REPO_MAP_TOKEN_BUDGET = 1500`
  (`server/src/modules/repo-intel/constants.ts:47`) і капи екстрактора конвенцій
  (`server/docs/specs/04-conventions.md:244-246`), але обидва про інший обсяг
  тексту. — default used: значення вище.
- `[NEEDS CLARIFICATION]` відсутність версіонування **б'є сильніше, ніж коли
  документи були лише для читання**: правка тихо змінює те, що бачить кожен
  прикріплений агент, історії немає, і відтворити промпт минулого запуску
  неможливо — `RunTrace.specs_read` зберігає імена, не тіла. Для скілів це
  вирішено знімками v(n+1) (`client/docs/specs/03-skills.md:57`); тут свідомо ні.
  — default used: без версіонування.
- `[NEEDS CLARIFICATION]` імпортований документ **не стежить** за своїм файлом у
  репозиторії: після імпорту це незалежна копія, і розходження ніде не видно
  (UX-2, UX-3 пропонують закрити). — default used: копія на момент імпорту.
- `[NEEDS CLARIFICATION]` конкурентні записи розв'язуються як last-write-wins
  (AC-40), без виявлення конфлікту: дві відкриті вкладки тихо перетирають одна
  одну. — default used: last-write-wins.
- `[NEEDS CLARIFICATION]` токенізація рахується одним кодуванням незалежно від
  моделі агента (`server/src/adapters/tokenizer/index.ts:38`). Для моделей поза
  OpenAI показане число — наближення, і фіча вперше зробить його видимим
  користувачеві. — default used: `cl100k_base` для всіх.
- `[NEEDS CLARIFICATION]` у репозиторії **немає стандарту доступності**: пошук по
  межах слів за `accessibility`, `a11y`, `WCAG`, `aria`, `keyboard`,
  `screen reader` по всіх одинадцяти спеках дає нуль збігів. NFR-6 у клієнтському
  файлі написано у спостережуваних термінах, але писати його немає проти чого.
